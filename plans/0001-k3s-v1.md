# K3s v1 — a single-node Kubernetes PaaS as a Package Skill

Status: accepted for implementation.
Date: 2026-08-01.

This document was saved before implementation. Like the other Package Skill
plans in this workspace, it records the decisions and safety constraints that
shape v1; once code exists, the code and tests are authoritative.

## Deliverables

Three layers will be created:

```text
green SDK + ONCE compute template
              ↓
getcolors/k3s                 green-only Package Skill
              ↓
getcolors/k3s-hetzner         desired state and copied launcher
              ↓
getcolors/k3s-helloworld      public app, image, manifests, and CD
```

The package repository is `getcolors/k3s`. It contains one skill,
`package-k3s-green`, and one launcher named `k3s`. The first consumer is the
existing `k3s-hetzner/` directory. The example application is the public
`getcolors/k3s-helloworld` repository.

## Scope and provider decision

V1 supports Hetzner Cloud compute only. It reuses ONCE's provider registry entry
and byte-identical `hcloud` compute template rather than copying them. The
backend remains selectable from ONCE's `local`, `s3`, and `r2` entries.

Restricting compute is deliberate. K3s listens on TCP 6443, and ONCE's generic
compute templates do not consistently own cloud firewalls. Claiming support for
a provider while leaving its Kubernetes API public, or while requiring an
undocumented pre-existing network rule, would be a broken security default.
Additional compute providers require their own tested firewall attachment before
they join the supported set.

K3s adds an `hcloud_firewall` and attachment beside ONCE's template. Inbound
rules allow SSH and public application traffic on 80/443 (plus ICMP); no rule
admits 6443. Unspecified inbound traffic is dropped and outbound traffic remains
allowed. The single-node design needs no inter-node Kubernetes ports.

## Desired state

The existing `k3s-hetzner/colors.yml` is the first complete configuration. Its
package-specific surface is:

```yaml
repository: https://github.com/getcolors/k3s-helloworld.git
k3s-version: v1.36.2+k3s1
flux-version: v2.9.2
```

`repository` is required, public HTTPS in v1, and watched by Flux. The branch
defaults to `main`; manifests default to `./k8s`. Private Git authentication is
out of scope. `k3s-version` and `flux-version` are explicit pins so two creates
months apart do not silently install different control planes.

The shared invariants stay unchanged: `colors.yml` carries no secrets;
credentials arrive only as `COLORS_PAR_*`; `COLORS_PAR_PROFILE` is refused;
`.colors/<profile>/` is generated output; real deletion requires a one-command
`COLORS_PAR_COMPUTE_PREVENT_DESTROY=false` override.

## Workflow and state

```text
create / build   start ─ k3s-compute ─┬─ k3s-ansible-local
                                      └─ k3s-ansible-remote

delete           start ─ k3s-ansible-cleanup ─ k3s-compute
```

The compute state key is `<profile>/k3s-compute.tfstate`. The package-specific
stage name is defence in depth against a profile collision with ONCE, walter, or
another package using the same R2 bucket.

The local stage owns its SSH block and marker; it does not reuse ONCE's local
playbook. The remote stage installs and converges K3s, Flux, and the Flux source.
On delete it only removes rendered files; destroying the VPS removes the remote
installation.

Build and `create --dry-run` render from desired state without contacting
Hetzner, R2, GitHub, or the target repository.

## K3s and Flux convergence

The remote playbook will:

1. verify SSH reachability;
2. install the exact K3s release with the installer from the matching Git tag;
3. keep K3s's bundled containerd, ServiceLB, and Traefik;
4. wait for the node to report Ready;
5. install the exact Flux release;
6. apply a `GitRepository` and `Kustomization` in `flux-system` for
   `repository`, branch `main`, path `./k8s`;
7. wait for the Flux source and deployment reconciliation to become Ready.

No kubeconfig is persisted under `.colors`: it contains a cluster client key and
is a credential. The zero-setup operator command is
`./k3s kubectl <arguments>`, which runs `sudo k3s kubectl` over the managed SSH
alias. Local manifests can be streamed with `-f -`. This keeps 6443 private and
requires neither a public API nor a durable local kubeconfig.

## Hello-world continuous deployment

`getcolors/k3s-helloworld` will contain:

- a tiny non-root HTTP container serving `/` and `/healthz` on port 8080;
- a pinned base image and Dockerfile;
- Kubernetes Namespace, Deployment, Service, hostless Traefik Ingress, and
  Kustomization manifests under `k8s/`;
- readiness/liveness probes, resource requests/limits, and a restrictive
  security context;
- GitHub Actions that build and smoke-test the image, publish `main` and the
  immutable commit SHA to GHCR, then commit the SHA into the Deployment
  manifest.

The manifest-only bot commit does not trigger another image build. Flux pulls
that commit and deploys it; GitHub receives no SSH key, kubeconfig, or access to
port 6443. The GHCR package is made public so the cluster needs no registry
credential. The hostless Ingress makes `http://<public-ip>/` useful immediately.
Domain-based HTTPS is a later desired-state extension.

## Regression and safety net

The package is green only, so it gets a golden harness rather than three-colour
parity. Tests will cover validation, provider credentials, graph shape, state
key, rendering, firewall rules, inventory, Flux objects, delete protection, and
the profile guard. Goldens will hold the full hcloud render under local and R2
backends and assert explicitly that:

- ONCE still declares `hcloud_server.node1`, which the firewall attachment uses;
- the compute stage remains `k3s-compute`;
- no ingress firewall rule opens 6443;
- Flux points at the desired repository and `./k8s`;
- no kubeconfig or provider secret is rendered.

The launcher gets the same contract handshake, pin task, and outside-checkout
harness as walter. It contains resolution and dispatch only; workflow and
kubectl behaviour remain in testable library namespaces.

## Execution and real-create gates

Implementation proceeds in this order:

1. create and test the local package source;
2. create `getcolors/k3s-helloworld`, push it, wait for its image workflow, and
   make the GHCR package public;
3. create and push `getcolors/k3s`, then stamp and push its launcher pin;
4. install the skill into `k3s-hetzner` through the real Skills installer and
   copy its launcher to the project root;
5. run package unit, golden, launcher, build, OpenTofu validation, and dry-run
   checks;
6. perform the real create with the supplied Hetzner and R2 credentials;
7. verify node Ready, Flux Ready, the public hello response, firewall closure of
   6443, and a second idempotent create;
8. record any provider-assigned immutable values needed to prevent future
   replacement, without writing credentials into source.

Real create is gated on all offline checks passing. Iteration may change the
implementation, tests, or generated fixtures, but it must not weaken the
security rules, state isolation, delete guard, or secret boundary to make a
failure disappear.
